# NixVet-FE — notas para o agente

Documentação de contexto de desenvolvimento para o Claude Code neste repositório. Complementa (não substitui) o que já está documentado em `DOCS/`. Atualize este arquivo quando fechar ou retomar uma iniciativa de várias sessões.

## Investigação: lentidão geral da plataforma (sessão 2026-08-25) — LEIA ANTES DE INVESTIGAR PERFORMANCE DE NOVO

Motivo da sessão: usuários reportando "cada clique demora uma eternidade" em produção, mesmo com respostas de API individualmente rápidas (50-70ms na aba Network). Sessão de investigação bem longa, com bastante caça a fantasma pelo meio — o resumo abaixo existe pra próxima sessão (ou próximo agente) não perder tempo redescobrindo os mesmos becos sem saída. Os itens de "descartado" têm evidência real por trás (prints, medição, bisecção de commit) — não é achismo.

### Causas reais, confirmadas com dado (não teoria)

1. **`fetchAllListPages` buscava página por página, sequencialmente** (`src/lib/pagination.ts`, usada por 16 hooks — pacientes, tutores, exames, áreas de exame, doenças, procedimentos, etc.). Visto ao vivo: 6 páginas de `/exams` a ~1s cada = ~8s somados só pra popular um filtro. **Corrigido**: agora busca em lotes paralelos (6 por vez). Já commitado.
2. **Lista de notificações sem limite no front** (`(app)/layout.tsx`, `NotificationsBell`). O backend tem um bug real (fora deste repo) que fica recriando o alerta "conversa aguardando resposta" do WhatsApp a cada ~5min pra uma mesma conversa travada, sem nunca marcar as anteriores como resolvidas nem deduplicar — isso já acumulou milhares de notificações "não lidas" pra uma clínica de teste. O front tentava renderizar a lista inteira de uma vez. **Corrigido no front** (trava defensiva em 50 itens, `visibleList = list.slice(0, 50)`), mas a causa raiz é backend — falta o mesmo dedupe que o alerta de `low_stock` já tem (`ClinicNotificationsService.existsUnreadFor`) pro tipo `conversation_alert`. Já commitado no front; **backend segue pendente**.
3. **Bundle sem code-splitting**: zero uso de `next/dynamic` no projeto inteiro antes desta sessão. `recharts` (6 páginas) e `@xyflow/react` (editor de chatbot-workflows) entravam inteiros no bundle da rota. **Corrigido**: gráficos e o editor visual agora são `dynamic(..., { ssr: false })`. `/chatbot-workflows/[id]` caiu de 272kB → 163kB de First Load JS; as páginas de financeiro com gráfico caíram ~100kB cada. Já commitado.
4. **Zero `loading.tsx`** em todo o app (nenhum route-level Suspense boundary). Adicionado um genérico em `(app)/loading.tsx` + um específico em `(app)/settings/loading.tsx` (pra não fazer a sidebar de Configurações sumir/reaparecer a cada troca de sub-rota). Já commitado.
5. **Fonte customizada "InterDoFigma" carregada errado** (`src/app/globals.css`): um `@font-face` cru apontando pra um TTF de 854KB em `public/fonts/`, sem preload, sem `next/font`, sem ajuste de fallback. Usada em 13 telas (títulos `font-extrabold`/`font-black`/`font-extralight`), sempre com peso 800/900/200 — nunca usando de fato a faixa variável 100-900 inteira que o arquivo carregava. Medido ao vivo no painel "Desempenho" do Chrome, produção: **LCP 3,02s e CLS 0,15** (ambos marcados "precisa melhorar"), com o próprio Chrome apontando o elemento do LCP como um `<p>` usando essa fonte. **Corrigido**: a fonte era literalmente o mesmo Inter que o projeto já carrega via `next/font/google` — só faltavam os pesos 200/800/900 na config. Adicionados ao `weight` do Inter em `src/app/layout.tsx`, `@font-face` customizado removido de `globals.css`, e a classe `font-['InterDoFigma']` removida das 13 telas (o `font-sans` herdado do `<body>` já resolve pro Inter certo). Resultado: pesos agora saem como `.woff2` subsetados por conjunto de caracteres (~336KB somando TODOS os pesos, e o navegador baixa só o subset que precisa — poucos KB tipicamente), em vez de 854KB de TTF obrigatório. **Ainda não commitado** (só está no working tree — 13 arquivos + `globals.css` + `layout.tsx`).
6. **~30-40 links do menu lateral fazendo prefetch automático simultâneo** (`<Link>` do Next.js pré-busca a rota assim que entra na viewport, por padrão). Contribuía pra sobrecarregar o roteador do Next em toda troca de página. **Corrigido**: `prefetch={false}` nos links do menu lateral em `(app)/layout.tsx`. Ajudou bastante (Agenda caiu de ~5100ms pra ~1600ms em teste local), mas não eliminou 100% — ver item 7. Já commitado.

### A causa raiz que sobrou: bug conhecido do roteador do Next.js 14.x

Depois de tudo acima corrigido, ainda sobra uma trava intermitente de **~5 segundos ao trocar de rota, sem NENHUMA requisição de rede e sem JavaScript bloqueado** (confirmado via CDP `Network.*` a nível de protocolo — zero eventos — e via um heartbeat de `setInterval(100ms)` injetado na página, que nunca parou de bater durante a trava). Isso bate com um bug documentado e não resolvido do App Router do Next.js 13.x–14.x ("stuck navigation" — o roteador cliente ocasionalmente perde a sincronia e só se recupera depois de alguns segundos, sem cair pra hard navigation). Ver [Issue #64609](https://github.com/vercel/next.js/issues/64609) e outras issues buscando `"Cannot remove node" "no matching node was found in the Store"` (esse erro específico é de OUTRA coisa, ver seção de falsos positivos — mas a categoria de bug do roteador é real e documentada separadamente).

**Confirmado por bisecção real de commit** (não só teoria): criei worktrees git em pontos diferentes do histórico (`fbae1e5~1` = ~5 dias atrás, `d79d624` = meio do caminho, `HEAD`), builds de produção completos, e medi tempo de clique-até-URL-mudar com Playwright automatizado (sem DevTools, sem extensão, ambiente limpo) em cada um:

| Página | 5 dias atrás | Logo após `d79d624` (i18n patients/owners/calendar) | HEAD (antes do fix de prefetch) |
|---|---|---|---|
| Agenda | 404ms | 5080ms | ~5100ms |
| Pacientes | 584ms | 3759ms | ~5045ms |
| Responsáveis | 161ms | 348ms | ~4737ms |
| Dashboard | **5036ms** (já quebrado) | 5059ms | ~5050ms |

Conclusão: o **Dashboard já tinha essa trava há pelo menos 5 dias** (bug do Next, preexistente, nada a ver com mudança recente). **Agenda e Pacientes pioraram de verdade** exatamente no commit que traduziu essas telas E adicionou `useCurrencyFormatter()` em cada preço da Agenda — mas o mecanismo não é "tradução é lenta", é que essas são as telas com MAIS itens renderizados de uma vez (a própria mensagem do commit chama a Agenda de "a maior página do app"), e mais trabalho de render por página aumenta a chance de bater na condição de corrida do bug do roteador. **Responsáveis foi traduzida no MESMO commit e não piorou** — reforça que não é "traduzir texto" em si, é volume de trabalho de render por página.

Next 14.2.35 é a **última versão que a série 14.x vai receber** (não vai sair mais patch). A correção definitiva é migrar pra uma versão mais nova (o Auroque onboarding e o QB do usuário já rodam Next 16, sem esse sintoma, mesmo o QB tendo um menu MAIOR que o do NixVet). **Tentei o upgrade nesta sessão** (`npx @next/codemod@latest upgrade latest` → Next 16.3.2 + React 19.2.8) e **revertei** — a ferramenta ficou presa num prompt interativo, e decidimos focar em achar a causa raiz de verdade antes de arcar com o risco de uma migração de major version (App Router mudou bastante entre 14→15→16, precisa de teste cuidadoso). Fica como **próximo passo recomendado**, mas como projeto à parte, não misturado com debugging.

### Falsos positivos descartados nesta sessão (evidência forte, não reabrir sem dado novo)

- **"Loop infinito de re-renderização" visto no React DevTools** (contador tipo "Anonymous x200000", subindo sem parar): é um **bug conhecido da própria extensão React Developer Tools** (testado na v7.0.1), não do nosso código. O erro `Uncaught Error: Cannot add/remove node "N" ... because no matching node was found in the Store` sai de dentro do arquivo da extensão (`chrome-extension://.../build/main.js`), é a extensão perdendo sincronia com sua própria cópia interna da árvore do DOM. Confirmado definitivamente: rodei o app localmente com Playwright automatizado (zero extensões) por 40s parado numa tela — 12 renders, zero problema. É um bug reportado dezenas de vezes no repo oficial do React (issues #24870, #34138, #31950, #23202, #25986...), sem correção publicada. **Se esse padrão aparecer de novo, não é bug nosso** — só vale investigar se acontecer também numa aba sem NENHUMA extensão de DevTools aberta.
- **Extensões de navegador corrompendo o DOM antes da hidratação** (erros React #418/#422 — hydration mismatch): também confirmado como extensão (não identificamos qual exatamente, mas some completamente ao desativar todas). Separado do bug acima. Se reaparecer, testar primeiro numa aba/perfil sem extensão nenhuma antes de suspeitar do código.
- **Quantidade de links do menu como causa única**: descartado como explicação isolada — o QB do usuário tem o dobro de links do NixVet e roda liso (mas está em Next 16). Fica só como fator agravante do bug do roteador (item 7 acima), não como causa raiz sozinha.
- **"Começou a acontecer depois que passamos a codar com Claude Code"**: verificado via `git log --follow -p -- package.json` — a versão do Next (14.2.35) está no **commit inicial do projeto** (20/02/2026) e nunca mudou. Não é uma regressão de versão recente.

### Metodologia útil pra retomar (funcionou bem, reaproveitar)

- **Bisecção real com git worktree**: `git worktree add /tmp/nixvet-X <commit>`, `.env.local` próprio apontando pra uma porta livre (3001, 3002...), `yarn install` + `yarn build` + `PORT=NNNN yarn start`. Backend local precisa de `CORS_ORIGINS=http://localhost:3000,http://localhost:3001,...` no `.env` do NixVet-BE (reverter depois pra `CORS_ORIGINS=` vazio) e reiniciar (`yarn --ignore-engines start:dev` — o `--ignore-engines` é necessário porque a máquina de dev tem Node 24, fora do range `>=20 <23` que o `package.json` exige).
- **Playwright sem instalar nada no projeto**: `npm install playwright` num diretório qualquer (ex: scratchpad) + `npx playwright install chromium`, depois um script Node simples com `chromium.launch()` + `page.click()`/`page.waitForURL()`/`page.on('request'|'console'|'pageerror')`. Login automatizado: preencher `input[name="tenantCode"|"email"|"password"]` e clicar `button[type="submit"]`. **Cuidado no Git Bash do Windows**: variáveis de ambiente tipo `/dashboard` viram path do Windows automaticamente — usar `MSYS_NO_PATHCONV=1` antes do comando.
- **Pra saber se o JS está travado ou só "esperando"**: injetar um heartbeat via `page.addInitScript()` com `setInterval(() => window.__hb(n++), 100)` + `page.exposeFunction`. Se o heartbeat nunca para, o thread principal está livre — a demora é outra coisa (rede, ou o roteador esperando por conta própria).
- **Pra ver rede a nível baixo** (mais confiável que os eventos de alto nível do Playwright): `context.newCDPSession(page)` + `cdp.send('Network.enable')` + escutar `Network.requestWillBeSent`/`loadingFinished`/`loadingFailed` diretamente. Pegou coisas que os eventos `page.on('request')` do Playwright não mostravam.
- **`ttf2woff2` via `npx`** funciona direto no Windows sem instalar nada (`npx ttf2woff2 < arquivo.ttf > arquivo.woff2`), útil pra confirmar hipótese de tamanho de fonte antes de migrar pra `next/font/local`.

## Iniciativa: responsividade mobile-first (modais + páginas) — EM ANDAMENTO

Objetivo: nenhuma tela deve ter scroll horizontal ou conteúdo cortado no mobile. Modais viram bottom sheet no mobile (desktop mantém o card centralizado de sempre). Iniciativa page-by-page seguindo a ordem do menu lateral — algumas páginas já cobertas, a maioria ainda não. Retome com uma varredura sistemática usando o checklist abaixo.

### Padrão de bottom sheet (feito — componentes compartilhados)

- `Dialog`/`DialogContent` (`src/components/ui/dialog.tsx`) e `AlertDialog`/`AlertDialogContent`: mobile-first por padrão (fixed bottom-0, largura cheia, só cantos de cima arredondados, handle de arraste), `md:` (768px) volta a ser o card centralizado de sempre. Animação via key-frames puras em `globals.css` (`dialog-slide-in-from-bottom`/`dialog-zoom-fade-in` etc.) — o projeto não tem plugin de animação do Tailwind, mesma técnica já usada pelo `Sheet`.
- **Gotcha real que já mordeu duas vezes**: Tailwind v4 aplica `translate-x-*`/`translate-y-*` na propriedade CSS `translate` (não mais dentro de `transform`). Se uma animação em `globals.css` também setar `transform: translate(...)`, as duas COMPÕEM e o deslocamento dobra (modal aparece cortado/fora de posição no desktop). Por isso `dialog.tsx` não usa mais `translate-x-[-50%]`/`translate-y-[-50%]` como classe Tailwind — o keyframe já define o `transform` final via `animation-fill-mode` implícito.
- `DashboardCreateFormDialog` (`src/components/dashboard-create-form-dialog.tsx`, ~32 telas): herda o bottom sheet do `Dialog` base. Largura padrão no desktop mudou de `calc(100%-4rem)` (quase tela cheia) para `md:max-w-2xl` — páginas que precisam de mais espaço (prévia lado a lado, tabela de itens) passam `contentClassName="md:max-w-3xl"` (ou similar) explicitamente; **nunca** usar `containerClassName` só pra encolher por fora, isso duplica a régua de largura em dois lugares e já causou telas com um "card dentro de card" de tamanho errado.
- A classe antiga `.modal-responsive` (hack "encolhe tudo com `!important`", ~18 arquivos) foi **removida** — estando fora de qualquer `@layer` do Tailwind, ela vencia incondicionalmente qualquer utilitário novo (unlayered > layered na cascata CSS), mesmo sem `!important`. Se algum dia reaparecer uma referência a ela, é resíduo — pode apagar.
- **Bug recorrente de breakpoint**: vários `Dialog` raw (não passam por `DashboardCreateFormDialog`) tinham `max-w-[calc(100%-2rem)] sm:max-w-XXX` (o `sm:` é 640px, ANTES do `md:` 768px onde o bottom sheet vira dialog centralizado) — entre 640–768px ficava num estado quebrado (dialog centralizado só que ainda com layout de bottom sheet por baixo). Sempre trocar `sm:max-w-*` por `md:max-w-*` e remover o `max-w-[calc(100%-2rem)]` manual (o `Dialog` base já cobre isso no mobile). Já corrigido em: `financeiro/orcamentos` (modal de detalhe), `ajuda` (2 modais). **Ao tocar em qualquer modal novo, `grep -n "sm:max-w" ` no arquivo primeiro.**

### Checklist ao revisar uma página nova (aprendido nas ~15 páginas já feitas)

1. **Cabeçalho** (título + botão de ação): trocar `flex items-center justify-between` por `flex flex-col gap-3 sm:flex-row sm:items-center sm:justify-between`, botão ganha `w-full sm:w-auto`.
2. **Linhas de filtro** (Select/Input lado a lado): por padrão empilhar `w-full` no mobile, `sm:w-auto`/`sm:w-[Npx]` no desktop. Se dois filtros devem dividir uma linha (ex.: Mês+Status em Contas a Pagar), usar `flex-1` nos dois dentro de um wrapper próprio, e `order-last` no filtro que deve sobrar sozinho embaixo (evita reordenar o DOM/desktop).
3. **Grids de cards/KPI**: geralmente já defaultam pra 1 coluna no mobile (grid sem `grid-cols-N` na base) — mas confira, alguns tinham `grid-cols-2` fixo na base (ex.: prontuários, análise de receita) forçando 2 colunas apertadas.
4. **Tabelas largas (4+ colunas)**: NUNCA confiar só em `overflow-x-auto` — o usuário validou que isso também é ruim pra mobile ("scroll horizontal não é indicado"). Padrão: `<div className="hidden md:block">` com a tabela original + `<div className="space-y-2 md:hidden">` com um card por linha (label+valor empilhados). Já convertido em: fluxo de caixa, custos de pagamento, planos de saúde (2 tabelas), análise de receita, orçamentos (detalhe).
5. **Gráficos Recharts**: dois bugs distintos, não confundir.
   - **Pie**: `label` externo (`label={formatPieLabel}`) estoura o card em telas estreitas (texto tipo "Boleto (34%)" flutuando fora do raio). Fix: `label={isMobile ? false : formatPieLabel}` (usar `useIsMobile(768)` de `@/hooks/use-mobile`), `outerRadius` menor, `Legend wrapperStyle={{ fontSize: 12 }}`, e envolver o `ResponsiveContainer` num `<div className="overflow-hidden">` como trava.
   - **Tooltip** (Bar/Line/Composed E Pie): a caixa padrão do Recharts não respeita a largura da tela — segue o dedo/cursor e pode estourar perto da borda. **NÃO remover o tooltip** (já tentei isso, usuário corrigiu: "não era a intenção, era reposicionar"). Fix certo: `allowEscapeViewBox={{ x: false, y: false }}` + `wrapperStyle={{ zIndex: 10 }}`, e pro caso do gráfico de Fluxo de Caixa (tooltip com várias linhas de texto) um `content={renderTooltip}` customizado com largura FIXA pequena (`w-40`) — combinado com `overflow-hidden` no wrapper do `ResponsiveContainer`, garante que nunca force scroll da página mesmo se o Recharts calcular a posição errado.
6. **Chaves de i18n faltando**: se o texto aparecer cru tipo `superadminFinance.kpis.aiCost.subAllTime` em vez de traduzido, o namespace inteiro pode não existir em nenhum idioma (aconteceu em `superadminFinance` — não tinha NENHUMA das ~65 chaves usadas, em nenhum dos 3 idiomas). Isso não é só estético: uma chave crua não tem espaços (só pontos), então não quebra linha e causa overflow horizontal de verdade. Sempre que uma página tiver overflow inexplicável, `grep` rapidinho se as chaves usadas existem no JSON antes de mexer em CSS.

## Iniciativa: módulo de Estoque completo

Objetivo: sair de uma "farmácia simples" (uma tabela `products` com nome/preço/estoque solto) para um estoque de verdade — categorias hierárquicas, fornecedores, ledger de movimentações, entrada de nota fiscal com Custo Médio Ponderado (CMP), débito automático ao aprovar orçamento/lançar custo de internação, alertas de estoque baixo, PDV (Balcão) de nível superior. `DOCS/modulo-estoque.md` é a documentação de referência (outro projeto, Next.js Server Actions + Supabase/RLS/RPC) — serve só como **referência conceitual de regra de negócio**, não como arquitetura a copiar; o NixVet é NestJS+Sequelize com toda lógica em application code (zero triggers/RPC de banco no projeto inteiro).

### Decisões de escopo já fechadas com o usuário (não reabrir)

1. Gestão de estoque (categorias/fornecedores/movimentações/nota fiscal) **fica dentro de Settings > Produtos** — não vira seção própria de nível superior.
2. Débito automático de estoque ao aprovar orçamento (`BudgetsService.approve`) e ao lançar custo de internação (`HospitalizationsService.createCost`) **entra no escopo** — NixVet não tem um "concluir atendimento" único como o projeto de referência, então são esses dois pontos que fazem esse papel.
3. Um **Balcão/PDV novo, de nível superior no menu** (grid de cards de produto → checkout) substitui o dialog simples de "Nova Venda" que hoje vive em `settings/produtos`.
4. Histórico de custo por produto **com gráfico** (Recharts já é dependência do projeto).

Fora de escopo (mesmo estando na doc de referência): leitor de código de barras via câmera/pistola/scanner remoto (só um campo de texto `internal_code`), comissão por venda de produto (não existe sistema de comissão no NixVet), drag-and-drop de categorização, rateio de frete/impostos, FIFO/PEPS.

### Status: as 5 fases entregues — módulo funcionalmente completo (não commitado ainda)

Entrega faseada, cada fase revisável isoladamente antes de avançar — todas testadas com scripts de smoke real contra o Postgres local (`tmp-smoke-*.ts` na raiz do `NixVet-BE`, rodados via `npx ts-node -r tsconfig-paths/register` e sempre apagados depois, nunca commitados):

- ✅ **Fase 1 — núcleo**: categorias (`product_categories`, 2 níveis, profundidade validada em `ProductCategoriesService`) + fornecedores (`suppliers`) + ledger append-only (`product_stock_movements`) + `products` ganhou `item_type`/`category_id`/`supplier_id`/`minimum_stock`/`internal_code`, e `stock_quantity` migrou de INTEGER pra `DECIMAL(12,4)` (insumo fracionado — ex. 2,5 ml — é rotina em internação veterinária). Motor único de mutação `StockService.mutateStock()` (`NixVet-BE/src/modules/products/stock.service.ts`) — todo caminho que mexe em estoque passa por ele, nunca deixa ficar negativo em modo `'strict'`. `ProductsService.createSale` já usa esse motor — fecha o bug antigo "permite negativo, controle fino fica pra depois". Frontend: `settings/produtos` ganhou abas Categorias/Fornecedores/Movimentações.
- ✅ **Fase 2 — entrada de nota fiscal + CMP**: tabelas `stock_entries`/`stock_entry_items`, `StockService.applyStockEntry`/`cancelStockEntry` (CMP recalculado em transação Sequelize, cancelamento com reversão de custo simplificada — só recalcula pelo caminho exato quando é a compra mais recente, sem replay retroativo em nota antiga). ### Gotchas técnicos (aprendidos nas 4 fases — não redescobrir)

- **Bug real em `INSERT ... SELECT` multi-linha com `:id` fixo em migration**: o padrão usado em `20260715113000-add-users-products-create-update-permissions.js` (propagar uma permissão nova pra todo `access_profile` que já tinha a permissão "fonte") gera **um único `uuidv4()` reaproveitado em todas as linhas** do `INSERT ... SELECT`. Como duas linhas com a mesma PK dentro do **mesmo** comando colidem e o `ON CONFLICT DO NOTHING` descarta tudo depois da primeira **silenciosamente** (sem erro), só o primeiro perfil correspondente recebe a permissão — confirmado ao vivo: rodar a migration nova (`20260821133000-add-stock-permissions.js`) só propagou pra `superadmin`, não pra `admin`/`manager`/etc., até eu trocar por um loop com um `INSERT` por linha (cada um com seu próprio `uuidv4()`), igual o padrão já usado em `attachPermissionsToProfile()` do seeder `20260715090000`. **Nunca copiar o padrão antigo de propagação em massa num único `INSERT...SELECT`** — sempre um `INSERT` por linha. A migration antiga não foi corrigida (já rodou em produção) — na prática funciona porque o seeder idempotente costuma rodar de novo no deploy e reconcilia o estado, mas é sorte, não corretude.
- **`products.stock_quantity` e toda coluna de quantidade de estoque são `DECIMAL(12,4)`, nunca `INTEGER`** — insumo/medicamento fracionado (ml, mg, meio comprimido) é rotina em internação. `StockService.round4()` arredonda toda operação a 4 casas antes de gravar, pra não acumular drift de ponto flutuante.
- **Migration de `ALTER COLUMN ... TYPE` em tabela existente**: testado com `db:migrate` + `db:migrate:undo` + `db:migrate` de novo contra o Postgres local, sem perda de dado — `USING stock_quantity::DECIMAL(12,4)` no `up`, `USING ROUND(stock_quantity)::INTEGER` no `down`.
- **`transaction.afterCommit(callback)` do Sequelize — nunca fire-and-forget**: a primeira versão do hook de notificação de estoque baixo era `t.afterCommit(() => { this.notifyLowStockIfNeeded(...).catch(...) })` — **sem `return`**. Isso deixa a promise interna solta: o runner de hooks do Sequelize só espera o que o callback *retorna*, então `mutateStock()` podia resolver (e o teste de smoke correspondente falhava, contagem de notificação vindo 0) **antes** da notificação realmente existir no banco — não é só um detalhe de teste, é uma condição de corrida real em produção também (ex.: uma resposta HTTP podendo voltar pro client antes do INSERT commitar). Corrigido trocando pra `t.afterCommit(() => this.notifyLowStockIfNeeded(...).catch(...))` (arrow function retornando a promise direto) — agora o Sequelize aguarda de verdade, e o `.catch()` interno garante que uma falha na notificação nunca derruba a mutação de estoque já commitada. **Qualquer `afterCommit` novo neste projeto precisa retornar a promise, nunca disparar sem aguardar.**
- **RBAC de menu é duplo e desconectado** (ver Fase 3 acima): `stock.*`/`products.*` (novo, granular, usado nos `@Permissions()` guards da API) não tem nenhuma relação com as chaves de menu (`products`, `balcao`, `financeiro-produtos` etc., usadas pela Sidebar/Command Palette/`+Novo`) — essas vêm de `getMenuPermissionsForRole(user.role)`, um sistema baseado em role string, mais antigo. Adicionar uma tela nova ao menu = editar os dois arquivos de `MENU_KEYS`/`MENU_BY_ROLE` (BE `core/rbac/permissions.ts` + FE `lib/role-permissions.ts`), não basta dar permissão no `access_profiles`.
- **`user.permissions` (as chaves de menu) fica preso em `localStorage` até relogar** — `SessionService.buildStaffSession()` (BE) recalcula `permissions` a cada login **e** a cada refresh de token (`AuthService.refreshSession` chama `buildStaffSession` de novo), então o backend sempre manda a lista atualizada. O problema é do lado do cliente: `renewSession()` (`NixVet-FE/src/lib/axios.ts`) só faz `POST /auth/refresh` e **descarta o corpo da resposta** (`.then(() => undefined)`) — nunca atualiza o `user` salvo em `localStorage`. Resultado: um usuário com sessão já aberta antes de uma chave nova ser adicionada ao menu (ex.: `balcao` na Fase 3) **não vê o item novo até deslogar e logar de novo** — não é bug de permissão nem de cache do Next, é `localStorage` desatualizado mesmo. Foi exatamente o que aconteceu comigo mesmo — usuário não achava o botão do Balcão logo depois dele ter sido adicionado. **Primeira coisa a perguntar quando "adicionei um item no menu e não aparece": já deslogou e logou de novo?** Antes de investigar RBAC/cache/build.

## Gotchas técnicos (aprendidos em sessões recentes — não redescobrir)

- **Traduções não atualizam em dev mesmo com o JSON certo**: `i18next.init()` (em [`src/lib/i18n/instance.ts`](src/lib/i18n/instance.ts)) só rodava uma vez por aba — o guard `if (!i18n.isInitialized)` bloqueava qualquer reload de recursos no Fast Refresh, então editar `locales/*.json` no meio de uma sessão de dev nunca aparecia sem reload manual completo (F5). **Corrigido**: agora, quando já inicializado, chama `i18n.addResourceBundle(lng, 'common', resources[lng].common, true, true)` pra cada idioma (só em dev, `NODE_ENV !== 'production'`). Se ainda aparecer chave crua tipo `prescriptions.form.x` na tela em vez do texto traduzido, é sinal de que essa correção quebrou ou de que o JSON tem erro de sintaxe — não é mais "precisa dar F5".
- **Alargar um `DashboardCreateFormDialog` não funciona via `containerClassName`**: essa prop só afeta um `<div>` interno que já é `w-full` do que o `DialogContent` externo renderizar — não tem efeito nenhum sozinha. O componente base do shadcn (`src/components/ui/dialog.tsx`) tem `sm:max-w-lg` (512px) cravado no `DialogContent`; pra vencer isso é obrigatório usar `contentClassName`, e o valor **precisa ter o mesmo prefixo `sm:`** (ex.: `contentClassName="sm:max-w-3xl"`), senão o `twMerge` não reconhece como o mesmo "grupo" de utility e o `sm:max-w-lg` do componente base continua ganhando na cascata. Pra caber sempre com folga sem estourar telas menores, usar `min()`: `max-w-[min(calc(100%-4rem),64rem)] sm:max-w-[min(calc(100%-4rem),64rem)]`. Pra forçar altura máxima (não só `h-fit` até o conteúdo crescer), passar `h-[90dvh]` no mesmo `contentClassName`.

## WhatsApp: mensagens apagadas ("Mensagem apagada")

"Apagar para todos" do WhatsApp chega da Z-API como um `ReceivedCallback` comum (não um evento separado), com `notification: "REVOKE"` no lugar de conteúdo de mensagem. **Não documentado com exemplo de payload pela Z-API** (confirmado direto na doc deles em 2026-08-21) — só a lista de tipos (`REVOKE`, `GROUP_CREATE`, `CALL_MISSED_VOICE` etc.) sob um campo `notification`, sem mostrar se `messageId` nesse evento é o id da mensagem revogada ou do próprio evento.

- Implementado defensivamente em `handleMessageRevoked()` (`NixVet-BE/src/modules/whatsapp/whatsapp.service.ts`): tenta casar tanto `body.messageId` quanto `body.notificationParameters[0]` contra `wam_id`. Se nenhum bater, loga `WARN "REVOKE recebido sem mensagem correspondente"` em vez de falhar silenciosamente — **se o recurso não estiver marcando mensagens reais como apagadas em produção, procurar esse log primeiro** pra descobrir qual dos dois campos a Z-API está realmente usando.
- Marca `whatsapp_messages.revoked_at` (migration `20260821120000-add-revoked-to-whatsapp-messages.js`) sem apagar `body_text`/`body_payload` — mantém histórico pra auditoria da clínica.   1. Começava com `max-height: 0 → 999px` (fixo) — ficava visivelmente travada porque o easing é calculado pra distância inteira (0→999px) mesmo o conteúdo real medindo uma fração disso, então quase todo o movimento "de verdade" acontece espremido numa fatia pequena da curva. Trocado por `grid-template-rows: 0fr → 1fr` (`grid` no wrapper, `overflow-hidden` + `min-h-0` no filho) — anima com base no tamanho real do conteúdo, não um teto arbitrário.
  2. Mesmo assim ainda tinha uma "travinha": o `padding-bottom` de safe-area (`calc(0.75rem+env(safe-area-inset-bottom))`) e a opacidade só existiam condicionalmente quando aberto — isso muda a altura *natural* do conteúdo no meio da transição (um salto discreto competindo com a transição suave de `grid-template-rows`) e faz duas propriedades (altura + opacidade) animarem em paralelo, que costuma ler como "engasgado" em vez de um movimento só. Fix final: `padding-bottom` sempre presente (incondicional) e **sem** transição de opacity — só a altura da track anima, ponto.
  3. **Regra geral pra qualquer collapse/accordion futuro neste app**: (a) nunca `max-height` fixo grande, usar `grid-template-rows: 0fr/1fr`; (b) nunca deixar padding/margin do conteúdo mudar condicionalmente junto com a transição — mantenha o padding fixo e deixe só a track do grid animar; (c) anime uma propriedade só — não some opacity + altura ao mesmo tempo esperando suavidade.
- **Balcão** ([`balcao/page.tsx`](<src/app/(app)/balcao/page.tsx>)): ganhou um botão "Estoque" no cabeçalho linkando direto pra `/settings/produtos` — atalho pedido pelo usuário porque, mesmo a gestão de estoque já existindo em Configurações, faz sentido ter acesso rápido a partir do PDV (ex.: perceber que faltou estoque no meio de uma venda).
